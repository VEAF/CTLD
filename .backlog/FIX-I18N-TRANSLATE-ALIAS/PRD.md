# FIX-I18N-TRANSLATE-ALIAS — 13 JTAC radio messages escape the i18n guard through the `ctld.i18n_translate` alias

**Status:** ✅ done (PR #269)

GitHub issue #265 (automated review of `develop` at `673b064`), decided with the maintainer on 2026-10-20: replace the alias in `src/`, check
that nothing in the code uses it any more, and keep it supported (defined and recognised by the guard) for the scripts outside the repository
that may still call it.

## Problem Statement

`ctld.i18n_translate` is a plain alias of `ctld.tr`. The dictionary generator (`generate_i18n_dicts.ps1`), the `i18n-guard` CI job and the
`pre-push` hook all rely on a scan for the literal name `ctld.tr(`, so everything written through the alias is invisible to the three of them.
`CTLD_jtac.lua` calls the alias 16 times (the JTAC radio messages): 13 of the 16 keys are in none of the four dictionaries. `ctld.tr` falls
back to the English key, so on a French, Spanish or Korean server every JTAC radio call comes out in English, with `lasing` / `standing by on`
inserted in the middle of a translated sentence. The gap widens on its own: the last batch of changes added two JTAC messages through the alias
that reached no dictionary, with no signal.

## Solution

The JTAC module calls `ctld.tr` like the rest of `src/`, so the guard sees its keys. The alias stays defined, for the scripts outside the
repository, and the generator also recognises it, so any key written through it still reaches the dictionaries. The 13 missing keys are added
to the four dictionaries and translated. A test locks the rule: every literal key passed to `ctld.tr` or to the alias in `src/` is a key of
the English dictionary.

## User Stories

1. As a player on a French, Spanish or Korean server, I want the JTAC radio messages in my language, so that I read one language in a sentence.
2. As a CTLD developer, I want one way of writing a translated text in `src/`, so that the guard sees every key.
3. As a mission maker with a script that calls `ctld.i18n_translate`, I want it to keep working, so that my mission does not break.
4. As a CTLD developer, I want the generator to also see keys written through the alias, so that a script or a plugin using it is not silently
   left out of the dictionaries.
5. As a CTLD developer, I want a test that fails when a literal key used in `src/` is missing from the English dictionary, so that this cannot
   happen again whatever the guard does.
6. As a maintainer, I want to know the alias has no remaining caller in `src/`.

## Implementation Decisions

- The 16 `ctld.i18n_translate(...)` calls of `CTLD_jtac.lua` become `ctld.tr(...)`; same arguments, same behaviour.
- The alias definition in `CTLD_i18n.lua` stays, with its comment now saying it is kept for external scripts (new code uses `ctld.tr`).
- The generator's key scan matches `ctld.tr` and `ctld.i18n_translate`.
- The dictionaries are regenerated by the build (13 new keys in `en`, stubs in `fr`/`es`/`ko`), then translated (proposal for the maintainer to
  review). `translation_version` is bumped by the generator.
- Documentation: the i18n developer page (EN + FR) says the alias is kept for external scripts and that the guard recognises it.
- No catalogue or configuration change.

## Testing Decisions

- A good test observes the invariant (every literal key is translatable), not how the scan is written.
- A busted spec reads the source files of `src/`, extracts the literals passed to `ctld.tr` and to the alias, and checks each is a key of the
  English dictionary. It fails before the change (the 13 JTAC keys) and passes after.
- The existing i18n specs and the `i18n-guard` job stay as they are.

## Out of Scope

- Removing the alias (it stays for external scripts).
- Translating keys not passed as a literal, or the config catalogue labels.
- Any change to the JTAC messages themselves.

## Further Notes

The legacy monolith (`migration/source/`, immutable) uses the alias heavily; it is not part of `src/` and not scanned.

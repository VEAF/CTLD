# 07 — `aircraftHoldBox` capability and shared box resolution

**Status:** ⬜ ready · **Type:** AFK

## Parent

[PRD — FIX-NATIVE-CARRY-DETECTION](../PRD.md). Stories 33, 34, 35, 38.

## What to build

A new **optional** per-type capability, `aircraftHoldBox`: a box in the aircraft's local frame
(x forward, y up, z right, metres) given by a minimum and a maximum corner. It is the zone in which a
cargo item counts as carried natively.

- **Resolution rule, shared by every native scan:** a type with a hold box uses it; a type without
  one uses the box DCS reports. One rule, one place.
- The vehicle entry (ticket 03) and the re-arm lock (ticket 05) read the resolved box.
- **Validation** rejects a malformed box: a missing corner or axis, or a minimum not below the
  maximum on every axis.
- **Schema:** the key, with English and French descriptions, in the configuration schema.
- **Editor:** the `ctld-tools` editor supports the key. Its form (nested table versus six scalar
  fields) is settled at the start of this ticket, after checking what the editor can already
  represent; the choice is recorded here.
- No default values ship in this ticket: they come with ticket 09.

## Acceptance criteria

- [ ] A configured hold box replaces the DCS box for vehicle entry and for the re-arm lock.
- [ ] A type with no hold box behaves exactly as before (DCS box).
- [ ] A malformed hold box is rejected by validation with a clear message.
- [ ] The schema, its English and French descriptions and the `ctld-tools` editor handle the key;
      the editor form chosen is noted in this file.
- [ ] i18n dictionaries regenerated by the build; the pre-push hook is green.
- [ ] Busted specs cover precedence, fallback and validation.
- [ ] `CHANGELOG.md` `[Unreleased]` has an `Added` entry.

## What to build

The configuration can say where an aircraft type's crates spawn, and how big a crate is.

- `capabilitiesByType` entries accept two optional fields: `crateSpawnSector` (`rear`, `side` or `front`) and
  `crateSpawnDistance` (metres from the aircraft centre to the first crate). The validation reports an unknown
  sector or a negative or non-numeric distance as an error, and a sector or a distance declared without the other
  as a warning; a zero distance is what the editor writes for an empty number, so it counts as undeclared. The
  editor and the schema show them.
- The crate size is a `size` field in each `spawnableCratesModels` entry (`ammo_cargo` is 1.31, a model with no
  size counts as 1.5), and a new setting `crateSpawnGap` (0.5 m).
- The default values for the five native-cargo types, derived from the collision shells: UH-1H side 3.0, Mi-8MT
  side 4.0, CH-47Fbl1 side 3.7, Mi-24P side 5.1, C-130J-30 rear 11.3. No other type gets a value.
- Reading helpers return a type's sector and distance, or nothing when it declares none, and a crate's size.

Nothing spawns differently yet: this slice only makes the values available.

## Acceptance criteria

- [ ] The five types carry their sector and distance in the default configuration; every other type carries none.
- [ ] A configuration with a bad sector or a negative distance is rejected by validation with a clear message; a
      half-declared plan is a warning; a zero distance is silent.
- [ ] The model `size` field and `crateSpawnGap` have defaults, schema entries and editor labels in English and
      French, and the editor writes and clears them.
- [ ] The generated defaults and `tests/ci/data/config_defaults.json` are regenerated by the project tools, not
      edited by hand; the round-trip spec passes.
- [ ] Busted specs cover the helpers (declared type, undeclared type, known and unknown crate size).
- [ ] `CHANGELOG.md` `[Unreleased]` has an `Added` entry.

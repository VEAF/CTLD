# 04 — remove the inert `category` from `spawnableCratesModels`

**Status:** done

## Why

All three crate models author `category: Cargos`
([src/CTLD_config.yaml:981-994](../../../src/CTLD_config.yaml#L981)) and the value never reaches DCS.
`_spawnStatic` builds the static data table from `model.type`, `model.canCargo` and
`model.shape_name` only — `category` is not copied
([CTLD_crate.lua:1713](../../../src/CTLD_crate.lua#L1713)). And even if it were, `dynAddStatic`
overwrites it: it honours a differently-named `categoryStatic` field and otherwise forces
`category = 'Cargos'`. The authored value is inert twice over and matches the forced value only by
coincidence.

Parity holds: the legacy monolith forced `'Cargos'` at the same point, so nothing changes in game.

This is the same class as the dead `AIZones` key PR #69 removed, and it violates the acceptance
criterion that lot set for itself.

## What changes

- `src/CTLD_config.yaml`: delete the three `category: Cargos` lines from `spawnableCratesModels`.
- `src/CTLD_config_schema.yaml`: if a `tableFields` entry or description mentions `category` for these
  models, remove it too.
- No engine change. Leave `dynAddStatic`'s `categoryStatic` handling alone — it is the real override
  hook and is used elsewhere.

## Acceptance

- `spawnableCratesModels` entries carry only `type`, `canCargo` and, for `sling`, `shape_name`.
- Crates still spawn with the same DCS static type as before (`ammo_cargo`, `container_cargo`).
- `version-gap` reports the removal, which is correct — an MM re-opening an older config should see it.

## Tests

- busted: a spawned crate's static data table is unchanged by the removal (assert on the table handed
  to `dynAddStatic` for each of the three model keys).
- The parity oracle (`tests/ci/data/config_defaults.json`) is regenerated by the build; confirm the
  three keys disappear from it and the parity test still passes.
